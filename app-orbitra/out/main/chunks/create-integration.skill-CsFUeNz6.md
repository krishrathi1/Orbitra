# Create or repair a code integration

Use this skill when the user asks for `/create-integration`, asks to automate a website action, or when an existing custom integration crashes, has an insufficient schema, or lacks a needed feature.

The entrypoint is always `/integrations/<slug>/index.ts`. Keep the default-exported integration metadata and ordered public `tools` array in that file so Orbitra can discover them. Supporting TypeScript, JavaScript, and JSON modules may live under the same `/integrations/<slug>/` directory and may be loaded with static relative imports. Orbitra bundles those modules before sandbox execution. Discovery is static: descriptor metadata must use literals, static objects and arrays, templates interpolating static primitives, or statically imported constants; never generate metadata with function calls or getters. Do not use dynamic imports, package or Node built-in imports, absolute imports, or paths that leave the integration directory. Treat `/` as the Orbitra profile root, not `$COMPANION_DIR`, the session directory, or the OS root. Do not create DAGs, manifests, standalone schema files, installers, duplicate integrations, or session-relative integration files.

The default export must include stable `id`, `name`, `description`, `rootDomain`, `domains`, and `tools` metadata. Set `rootDomain` to the product's registrable domain only, such as `wix.com`, with no protocol, subdomain, port, or path. Orbitra uses it as the integration identity and favicon source in settings, mentions, and action cards. Keep `domains` as the complete host allowlist needed by the tools; it may contain subdomains such as `manage.wix.com`.

## Module architecture

- Keep a genuinely small one-tool integration in `index.ts`. For two or more substantial public tools, or when one action has distinct browser/network phases, use the multi-file system instead of growing a monolith.
- Keep `index.ts` as a thin discovery boundary: import one complete tool descriptor per substantial action, declare integration metadata, and expose those descriptors in the ordered `tools` array. Keep each action's schema, permission classification, execution, and verification together in its tool module.
- Default to one module per substantial user capability, such as `actions/search-people.ts` or `actions/send-message.ts`. A module owns that action's complete internal workflow, including prerequisites, navigation, exact target resolution, the action, and its postcondition.
- Extract only genuinely shared, stateless helpers such as tab acquisition, domain guards, canonical URL parsing, and common result types. Keep action-specific selectors, constants, and diagnostics beside the action that uses them. Avoid catch-all helper files, import cycles, and mutable module-level runtime state.
- Group several small actions in one domain module only when they operate on the same resource and share real invariants. Split by public capability and reason to change, not arbitrary file size.
- File boundaries are internal implementation details. Never turn navigation, search, or setup phases into required public tool choreography: every public tool still satisfies the one-call action contract.
- When modularizing an existing integration, preserve its id, tool names, schemas, behavior, and error semantics. Move code in reviewable steps and re-run discovery plus every tool's executable verification after the final import graph is in place.

## Permission policy

- Every public tool must declare `requiresPermission: true | false` beside `executionMode` in its descriptor. This plugs the action into Orbitra's existing per-tool permission system; never implement a custom confirmation dialog or permission store inside integration code.
- Use `false` only for strictly observational actions that do not change remote or local data, send or publish user content, submit a form, upload or download a file, start a purchase, alter a subscription, or trigger another external side effect. Opening or navigating an owned browser page solely to collect read-only results does not by itself require permission.
- Use `true` for create, update, delete, send, reply, post, comment, react, like, follow, unfollow, connect, accept, ignore, withdraw, upload, download, purchase, submit, and every other consequential or ambiguous action. When uncertain, use `true`.
- `requiresPermission: true` delegates to Orbitra's normal `Ask every time`, `Always allow`, and `Disable action` rules. `false` skips the approval prompt. A missing declaration is invalid.
- `__dry_run: true` remains permission-free because it must not perform the action. Do not use dry-run behavior as a reason to classify a normal mutating call as permission-free.

## Maintained reference integration

Orbitra ships `/integrations/linkedin/index.ts` as the maintained reference for high-quality interaction integrations. Read it when building or repairing an interaction tool. Its people, conversation, invitation, follow, and post tools demonstrate complete resource lifecycles. Reuse its general patterns: one-call action ownership, optional tab hints, safe owned-page acquisition, bounded domain collections, stable URL identity, locale-independent control selection, entity-bound mutation scope, optional fields that represent real variants such as a connection note, strict element handles, reactive-editor state verification, single final activation, and non-sensitive postcondition checks.

LinkedIn's one-recipient mutation boundary and exact challenge/restriction checks are site-specific safety measures. Do not copy them as boilerplate for ordinary sites. Interaction-only transport is required for any site established as bot-detection-heavy: use the browser UI, allow only the requests made naturally by that UI, and never generate or replay direct requests. Never copy LinkedIn selectors or attempt to bypass a challenge.

## Multilingual websites

- Treat every website that offers multiple interface languages as multilingual even when the manual proof uses English. Record the observed document/site locale with the proof and assume another user may run the integration under a different locale.
- Keep control, readiness, empty-state, guard, and postcondition logic independent of translated copy. Prefer validated routes and href shapes, stable product-owned ids/data attributes/component keys, roles without translated names, structural parent-child relationships, and element state.
- Do not hardcode or enumerate translations for action labels, accessible names, placeholders, weekdays, relationship/status suffixes, empty-result messages, toasts, restriction banners, or confirmation copy. A translation dictionary is not a durable selector strategy.
- Text matching is appropriate for user-supplied content and exact resource identity, such as a person name, query, message, or comment. Normalize surrounding locale-formatted decorations generically instead of listing language-specific values.
- Add a user-facing `language` or `locale` input only when language changes the requested business result, such as choosing a translation or regional dataset. Never require it merely so the tool can find controls.
- Preserve localized text returned as data when it helps the user, but do not parse translated prose to decide which action to perform. Safety and challenge detection must also use locale-independent evidence.

## One-call action contract

Each public tool must complete the user's requested action in one invocation. Internal browser work is implementation detail, not a sequence the calling companion must perform first.

- A tool such as `send_message({ person_name, message })` must find or open the relevant signed-in site, resolve the exact person, open the right conversation, send once, and verify the result. Do not require the companion to call a search tool first, open a profile manually, prepare a composer, or pass an opaque tab id before invoking it.
- Expose user-known semantic inputs. Names, messages, URLs the user supplied, and explicit account choices belong in `inputSchema`. Discoverable browser state does not.
- Interaction tools may declare `agentInputSchema.tab_id` as an optional optimization for reusing a known tab, but it must not be required. When it is absent, resolve the tab inside `execute(input, orbitra)` with `orbitra.listTabs()`; reuse an unambiguous matching tab or create one with `orbitra.openTab({ url, reuse_existing: false })`, then navigate and finish the workflow through strict locators. Independent or concurrent tool invocations must not share a navigable working page implicitly.
- A profile or resource URL may be an optional disambiguation hint, but do not require one when the site can search by the user's semantic target. Fail closed and request semantic clarification only when multiple candidates remain genuinely ambiguous.
- Do not tell the user to open or navigate to a page unless the integration has already attempted its own tab acquisition and reached a prerequisite only the user can complete, such as sign-in, CAPTCHA, or account selection.
- The normal confirmation card for the public tool is the only user-visible action boundary. Discovery, tab acquisition, navigation, and postcondition checks stay inside the approved invocation.

## Resource lifecycle design

- Model the practical lifecycle implied by the requested use case. Collection workflows need a bounded list tool; detail workflows need a zero-or-one read tool; mutations need an exact target and a verified postcondition. Examples include list → read → reply for conversations and list → accept/ignore/withdraw for invitations.
- A list tool returns a domain-named collection such as `candidates`, `conversations`, `invitations`, or `posts`. Every item carries the stable identifier or canonical resource URL needed for later exact actions plus concise visible context. Return limit, visible count, truncation, and pagination metadata that the site actually exposes.
- Stable IDs and resource URLs returned by reads should be accepted by matching mutations as optional exact fast paths. They do not replace semantic inputs or make a preliminary read mandatory: a direct mutation still owns target discovery when the user provides only a name or other human-level identity.
- Multiple collection results are successful data. Never force a list or search tool to choose one result, and never turn ordinary multiplicity into an ambiguity error.

## Fast-path discipline

- Before searching or navigating, check whether the selected working page already has the validated target URL and exact entity identity. When the caller supplies a stable resource URL, use it directly after host/path validation. Navigate only when the current URL differs.
- Read independent passive state concurrently and preserve deterministic result order. Good candidates include tab URLs, repeated search cards, guard text, and mutually exclusive success states.
- Browser-backed extraction may have lower concurrency limits for particular websites plus a profile-wide ceiling. Keep one research workload together and let the runtime queue excess `orbitra.extract` pages; never open extra tabs or agents to bypass that scheduler. Integration results must remain correct when a page starts later than its siblings.
- Do not spend a full timeout on one selector before trying an equivalent fallback. Put equivalent durable CSS variants in one target, or race strict identity-equivalent locators and accept the first unique match. Never make speed by weakening strictness, choosing by position, or racing controls that could represent different actions.
- Wait on meaningful conditions rather than fixed delays. Re-resolve only after navigation or a DOM-replacing transition; otherwise retain the verified entity scope for the next immediate step.

## Execution and approval

A direct request to create, repair, or extend an integration is approval to begin this workflow. Do not switch to Plan mode or ask for a second "Ready to start?" solely because the workflow is new, writes an integration file, or starts the integration miner.

For safe, non-sensitive browser actions, perform the manual proof immediately. Clarify first when the human-level target or action is materially ambiguous. If the manual proof would itself perform a sensitive, destructive, or externally consequential action, such as sending a message or submitting a form, obtain the normal confirmation for that action before performing it; creating the integration file and running non-mutating verification do not need a separate confirmation.

## Parent-agent flow

1. Prove and classify the request.
   - Decompose the requested scope into one row per proposed public tool. For each row record the exact manual steps, stable target identity, visible success signal, and tabs used. Treat this capability evidence ledger as a release gate, not planning notes.
   - Perform every requested tool's action manually in the browser first. This proves the current UI flow and captures network evidence before code is written. Do not make the integration attempt the first experiment.
   - Record the document/site locale used for the proof and whether the site exposes other interface languages. Multilingual sites must be designed for locale-independent execution even if only one locale is currently open.
   - Manual proof is capability-specific. A successful search does not prove a home feed, detail read, post composer, like, repost, reply, delete, or any other adjacent action. A reversible typing probe proves editor mechanics but does not replace an approved manual submission and observed postcondition.
   - For an externally consequential proof, obtain the normal confirmation before performing the exact manual action. If the user does not approve that proof, mark the capability unproven and do not generate or advertise that tool yet.
   - Spawn the miner only with capabilities whose ledger rows passed. For a multi-tool request, prove every row before one combined miner run or patch the integration incrementally as additional rows pass.
   - When the action was just completed manually, spawn the miner with the user intent, capability evidence ledger, exact manual steps, visible success signal, and tabs used.
   - When a custom integration fails or lacks a needed feature, continue manually in the browser first. After the manual action succeeds, spawn the miner to patch the existing integration using the new page and network evidence.
   - If the user request is ambiguous, clarify the human-level target/action before spawning.

2. Capture tab context explicitly.
   Use `orbitra.listTabs()` to identify relevant tab ids by URL/title/context. Prefer explicit `tabId` over active-tab inheritance. If multiple tabs were involved, pass the primary one via `tabId` and list every relevant tab in the prompt.

3. Spawn the miner.
   Run the snippet in a foreground `execute_code` call with `run_in_background: false` and await the result. Do not end the parent turn or report that the integration is ready while the miner is still running.

4. Interpret the result.
   - If the miner reports `passed-static-review`, report the path and tool names.
   - Treat `failed-static-review` and `insufficient-history` as terminal release failures. Do not invoke the generated tools normally, ask the user to try them, advertise them as ready, or treat a partially passing tool as released. Repair from new manual evidence and re-run the complete verification loop, or report the concrete blocker.
   - A combined integration passes only when every tool in the requested scope has a passed capability-ledger row and its required executable probes pass. If one tool is still unproven or failing, either remove it from this release and re-run validation for the reduced declared scope, or keep the entire requested scope unreleased.
   - If the miner says the action cannot be integrated, make sure it patched the artifact to document that limitation with comments in `/integrations/<slug>/index.ts` and clear description text.
   - When replying to the user, translate technical miner results into plain English. Do not repeat probe lists, schema names, JWT/XSRF/auth header details, endpoint paths, or `orbitra.help` internals unless the user asks. Say what is now possible, what the user needs to do, and any important limitation.

## Miner instructions to include

- Inspect both `<network_forensics>` SQLite evidence and the live tab used for the proven manual action. Start network inspection with `PRAGMA table_info(network_events)`; do not guess hosts, endpoints, or DOM selectors.
- Declare per-tool `executionMode: "network" | "interaction" | "hybrid"`. Prefer network only when an observed request can be reconstructed safely. Use interaction for UI-only/opaque actions. Use hybrid only when the reliable flow genuinely needs both.
- Declare per-tool `requiresPermission: true | false` beside `executionMode`. Use `false` only for strictly observational read-only actions without external or local side effects. Use `true` for mutations, submissions, messages, uploads/downloads, purchases, and ambiguous actions. `true` must use Orbitra's existing per-tool permission rules; do not add a custom confirmation flow. A missing declaration is invalid.
- BOT_DETECTION_TRANSPORT_POLICY: when credible manual-flow evidence, repeated challenge behavior, maintained product policy, or known site constraints establish that a site is bot-detection-heavy, executionMode=interaction; directRequests=forbidden; observedRequestReplay=forbidden; challengeBypass=forbidden; overridesDefaultSelection=true. The site's own browser UI may trigger its normal page requests. Treat this as a transport requirement once the classification is established, not as a soft preference. Network evidence may explain page state and locator choices, but must not become generated request code for that site.
- LINKEDIN_TRANSPORT_POLICY: hosts=linkedin.com,\*.linkedin.com; executionMode=interaction; directRequests=forbidden; observedRequestReplay=forbidden; overridesDefaultSelection=true. Browser UI actions may trigger LinkedIn's own page requests. Implement LinkedIn tools exclusively through live browser locators and actions. Network evidence may explain page state, but must not become generated request code.
- Treat the shipped `/integrations/linkedin/index.ts` as the maintained interaction reference. Reuse its general action-ownership, result-cardinality, identity-binding, editor-state, and postcondition patterns. Its exact challenge/restriction guardrails are not generic boilerplate; apply site-specific checks only from evidence, never by copying LinkedIn selectors or bypass behavior.
- Use the multi-file system for integrations with multiple substantial actions. Keep `index.ts` thin, place each action's complete workflow in a focused module, and share only stateless helpers or domain types used by more than one action. Keep action-specific selectors and diagnostics local to that action.
- A file split must not become tool choreography. Each imported action handler still owns its prerequisites, navigation, target resolution, action, and postcondition; do not expose internal setup steps as required public tools.
- Build fast paths without weakening identity or safety: validate the current page and any supplied stable resource URL before searching; navigate only when the current URL differs; read independent passive state concurrently while preserving result order; combine equivalent durable CSS variants or race strict identity-equivalent locator waits instead of consuming a full timeout per fallback; and wait on state transitions rather than fixed delays.
- Interaction tools must resolve their working tab internally, then use `orbitra.tab(resolvedTabId).locator(...)`. Start with an optional supplied `tab_id`, reuse exactly one suitable matching signed-in tab, and otherwise use `orbitra.openTab({ url, controlled_by: "agent", focus: false, reuse_existing: false })`. `reuse_existing` defaults to true for ordinary retry-loop protection; set it to false for an owned working page whose navigation state must be isolated from independent or concurrent tool calls. When zero or several reusable tabs exist and the tool can establish its own context by navigation, open a fresh agent-controlled working page instead of asking the user to choose. Ask for semantic clarification only when the request depends on existing page-specific state such as a draft, selection, or explicitly referenced open page. Never choose arbitrarily among ambiguous user tabs. Browser-agent tabs remain attached, unthrottled, and rendered at a full-window viewport beneath the Orbitra UI, so locator actions must work without calling `tab.focus()`. Use `focus()` only when the action explicitly needs to make that page user-visible or use active-tab-only visual state. Keep dry-runs passive. Locators are strict by default and wait for one unique match within the timeout; persistent ambiguity must fail rather than type or click the wrong element.
- Design output cardinality from the tool verb before choosing locators: search/list/browse returns zero-to-many results; get/resolve/read-detail returns zero-or-one; send/update/delete and other consequential tools require exactly one verified target.
- Search/list tools must return a bounded, deduplicated domain-named collection such as `candidates`, `conversations`, `invitations`, or `posts`. Each item needs a stable identifier or resource URL and concise visible identity details. Return page/limit/`visibleCount`/`truncated`/`hasMore` metadata that matches the site's real pagination or bounded surface. Multiple matches are successful data, not an exception.
- When repeated result cards can contain nested cards of the same resource type, identify the exact collection container and enumerate only its direct logical result roots. Read each item's canonical URL, visible text, author/resource identity, and action controls from that same root. Exclude nested quotes, replies, previews, embeds, and promos unless the tool explicitly promises them. Verify this on a live page containing nested content when the surface supports it; do not use a broad page-wide repeated-element selector whose descendants can be counted as sibling results.
- When the requested use case spans a resource lifecycle, expose the smallest useful read/list and mutation surface together. Carry canonical identifiers or URLs from read results into matching mutations as optional fast paths, while keeping each direct mutation independently capable of semantic target discovery.
- A consequential tool that searches internally may proceed only with one exact candidate; otherwise return `requiresDisambiguation: true` with the same candidate shape and perform no mutation. Positional iteration with `count()` plus `nth()` is allowed only while passively enumerating a stable repeated-result container; carry the candidate's stable identifier or URL into later actions.
- Before interacting, resolve the current element explicitly with `const element = await tab.find(target, { state: "visible" | "enabled" | "disabled" })` or `await locator.find(...)`, then call `element.click()`, `element.type(...)`, or `element.waitFor(...)`. On multilingual sites, prefer validated routes and href shapes, test IDs, durable product-owned attributes, roles without translated names, stable structural CSS, and control state. Use exact visible text or accessible names only for user-supplied content or resource identity, not translated action copy. CSS describes structure, not the intended recipient/resource by itself. Avoid generated/hashed classes, absolute DOM paths, broad positional selectors, and `first()`/`nth()` guesses. Use `count({ state? })` only for passive investigation. Resolve a new handle after navigation or a DOM-replacing transition.
- Every locator clause must come from the live state or captured evidence for that exact flow. Probe the complete readiness and action targets before writing them. Do not invent likely roles, accessible names, attributes, URL fragments, or selected-state markers. If an attribute such as `href` is not exposed as reliable locator evidence, resolve the element through an observed stable signal, read the live attribute from the exact handle, validate it, and only then use the value.
- When an exact action control is an anchor with an observed same-site destination, read its live `href`, validate the origin, path, expected query shape, and entity binding, then prefer `tab.goto(validatedHref)` when a synthetic click does not reliably produce the transition. Never construct a private route from guessed identifiers or accept an unrelated destination. Buttons and links without a safely validated destination still use a real click followed by an explicit post-click state wait.
- Bind every mutating parent to the user's intended entity before resolving it. A generic form/dialog/row followed by an identity check is insufficient. Use `locator.filter({ has, hasNot, hasText, hasNotText })` to filter the structural parent by an exact relative descendant identity, then call `.find(...)`. Example: `const identityTarget = { role: "heading", name: personName, exact: true }; const composerLocator = tab.locator({ css: "form" }).filter({ has: identityTarget }); const composer = await composerLocator.find({ state: "visible" })`. Resolve the editor and submit only inside that identity-bound parent. Immediately before the final click, re-resolve the parent identity and enabled submit control in the same scope. Never use a page-wide submit selector.
- For an exact search-result or resource link, read its `href` from the resolved handle, validate the destination host/path, navigate with `tab.goto(destination)`, then wait for the exact destination identity before continuing. A completed click is not proof that navigation finished; never inspect the old page immediately after a navigation-triggering click.
- Treat `contenteditable` as a distinct input class. Match it with `[contenteditable]`, resolve it with `.find({ state: "enabled" })`, use the returned handle's `.type(text, { replace: true })`, and verify the same handle with `.waitFor({ state: "value", value: text })` before waiting for the scoped submit handle to become enabled. Do not treat a completed type/fill call as proof that a reactive editor accepted the text.
- Patch matching existing integrations; do not create a duplicate integration for the same product/API family.
- Create or patch only the requested tool(s). Related observed endpoints may be used as evidence for runtime resolvers, cookies, headers, IDs, page/account context, and prerequisites, but they are not permission to add list/update/delete/extra tools.
- Classify fields: user-known values in `inputSchema`; opaque/internal/runtime values in `agentInputSchema` with `agentInputContract`.
- Browser-session tools need per-tool `runtimePrerequisites` describing genuine user-owned requirements such as a signed-in browser session. Do not describe an already-open or pre-navigated tab as a prerequisite when the tool can find, open, or navigate one itself.
- Every tool must include optional `__dry_run: boolean` in `inputSchema`. In dry-run mode it must run validation and prerequisites. Network tools resolve evidence and construct the request without sending it. Interaction tools must resolve every locator with `.waitFor(...)` and return bounded element diagnostics without typing, clicking, or submitting.
- For interaction and hybrid tools, declare `tab_id` as an optional agent-input hint for compatibility, with a contract that says the caller must omit it when no suitable tab is already known and must not ask the user for a raw id. Semantic clarification is allowed only when existing page-specific state materially affects the action. Never include `tab_id` in `agentInputSchema.required`. Runtime code receives `execute(input, orbitra)` and must resolve or open its own tab when the hint is absent or stale.
- Do not split one user intent across public tools. A standalone search tool may exist, but send/read/connect/update tools must perform any necessary search and navigation internally rather than requiring a preceding search call.
- Keep dry-runs passive. They may inspect and reuse an existing matching tab, but must not open a new tab, navigate, type, click, or submit. If no matching tab exists during verification, return bounded resolver diagnostics while normal execution still owns tab acquisition.
- Generated runtime errors must be debuggable by the calling agent. Include bounded, redacted context such as failing resolver/helper, tab_id, expected host/path/header names, SQL row counts, returned column names, available keys, parse/status error, and next action. Do not include raw cookies, auth headers, tokens, CSRF values, full bodies, or full user payloads.
- Do not invoke generated mutating tools or activate their final submit controls during creation or repair.
- For every tool that submits typed text, run a separate reversible pre-submit probe after writing the integration; passive `__dry_run` is not enough. Open a fresh empty composer, resolve one identity-bound strict composer root, confirm the editor is empty, and wait for the composer-scoped submit control with `.waitFor({ state: "disabled" })`. Then use the tool's typing primitive to enter a unique harmless temporary string. Wait for the editor's exact value, then for the scoped submit control to become enabled. In `finally`, clear the editor, wait for an exactly empty value, and wait for submit to return to disabled. Never click submit. Do not disturb a pre-existing draft, and never pass verification if cleanup is unproven. When the site permits it without changing external data, preserve or open a second unrelated composer/dialog/row and prove the identity-bound parent remains unique; otherwise prove from the locator definition that it contains an exact user/resource identity rather than position or visibility alone.
- For every search/list tool, run a safe live query with multiple visible results. It passes only if the tool returns at least two deduplicated collection items with stable identifiers or URLs and bounded pagination/truncation metadata, without treating multiplicity as an error or causing a mutation.
- Verify with executable probes, interface validation, public help rendering, and each generated tool with `__dry_run: true` plus safe representative required inputs. For interaction tools, this must prove the current page has one unambiguous visible/enabled target for every action step; text-submission tools must additionally pass the reversible state-transition probe. If any probe fails, repair and re-run.
- Confirm validation and help report the intended permission policy for every tool. Run permission-free read tools normally and verify they do not suspend for approval. Do not invoke mutating tools during creation; verify their `requiresPermission: true` declaration and use the existing reversible pre-submit probe instead.
- For a multi-file integration, run discovery, validation, help, and every declared tool's required executable probe after the final file split. This is the proof that Orbitra compiled the complete import graph and that no imported action module or shared helper was left broken.
- For every multilingual interaction surface, audit the finished source for translated selector/state dependencies.
